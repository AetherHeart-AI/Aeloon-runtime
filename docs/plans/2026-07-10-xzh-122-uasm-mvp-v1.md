# XZH-122: UASM MVP v1.0 implementation plan

## Goal

Add an opt-in Unified Agentic State Machine (UASM) runtime to `aeloon-core`
without rewriting the existing provider, tool registry, task graph, session, or
deterministic loop-guard behavior. The current kernel remains the A1 baseline;
the new runtime makes state, transitions, token attribution, forward context,
and temporary LLM guard decisions explicit and independently measurable.

## Baseline and constraints

- Baseline commit: `461ae1c`.
- Baseline checks: `68 passed`; Ruff clean.
- Preserve the public `run_agent_kernel(...) -> (final_content, tools_used,
  messages)` API and its current behavior.
- Preserve the existing backward compaction hook: its returned messages replace
  canonical history and must remain persistable.
- Forward minimal-context processing produces a model-call view only. It must
  never replace canonical messages or split an assistant tool call from its tool
  results.
- Reuse `AgentLoopGuard` decisions and `task_graph` execution. Do not generalize
  the mutable tool `TaskNode` into an Agent node.
- All terminal paths in the UASM runtime produce visible final text.
- TemporaryGuard receives structured bounded evidence, never the raw transcript.
- Profile files, compiler, semantic tool grouping, persistent harness agents,
  and a new mixed fallback framework remain out of scope.

## Architecture

### 1. Lightweight state and explicit transitions

Create `aeloon_core/state.py` with:

- `AgentNode`: `master`, `worker`, `tool`, `temporary_guard`, `done`.
- `RunStatus`: `running`, `finalizing`, `completed`,
  `terminated_by_rule`, `terminated_by_guard`, `failed`.
- `StateMetadata`: phase/status, iteration and finalization counters,
  finalization prompt, final content, termination reason, and experiment labels.
- `LazyValue`/lazy references for large tool results and other deferred payloads.
- `LightweightState`: canonical messages, current minimal context,
  permissions, active tool names, metadata, guard state, pending response/tool
  work, tools used, transition records, and token ledger.
- A stable digest derived from serializable state summaries rather than raw
  object identity.

Move mutable rule counters into a `LoopGuardState` object that can be owned by
`LightweightState`; keep compatibility properties on `AgentLoopGuard` for the
existing tests and API.

Create `aeloon_core/agents.py` with a common async `BaseAgent.run(state) -> state`
contract and deterministic `MasterAgent`, model-calling `WorkerAgent`, and
task-graph-backed `ToolAgent`. The runner records every node transition and
routes only through `MasterAgent` decisions.

### 2. Transition trace and token attribution

Create `aeloon_core/transitions.py` with:

- `NodeKind`: `domain`, `harness`, `context_processing`.
- `TransitionRecord`: schema version, session/turn id, sequence, iteration,
  node, node kind, before/after digest, decision, token usage, and wall time.
- `TokenLedger`: totals plus per-node-kind counters.
- `TransitionRecorder`: in-memory accumulation plus an optional persistence
  callback.

Store transitions in `data_dir/traces/<session-id>.jsonl`, not in the existing
session JSONL. Add `SessionStore.append_transition()` and trace loading helpers.
Persist turn-level usage totals/by-node-kind in the normal turn record.

Domain calls use `LLMResponse.usage`. TemporaryGuard calls are attributed to
`harness`. Context compaction returns its summarizer usage and is attributed to
`context_processing`. The pure forward processor records estimated before/after
input tokens without claiming provider-billed completion tokens.

Update terminal progress accounting to aggregate all LLM responses in a turn
instead of displaying only the last response.

### 3. TemporaryGuard and deterministic rule escalation

Add `aeloon_core/temporary_guard.py` with:

- `GuardEvidence`: event/reason, current phase and budgets, bounded recent
  failures, state digest, and minimal-context statistics.
- `GuardResolution`: chosen `LoopGuardDecision`, source, usage, and fallback flag.
- Stateless `TemporaryGuard` that makes one tool-free JSON response call.

The guard reuses the closed `LoopGuardAction` space. In binary mode it accepts
continue/terminate and compiles them to return-to-model/stop; full mode accepts
the safe applicable action set. Prompts and visible final text are compiled
locally, not trusted verbatim from the model.

Only an escalation-eligible deterministic `STOP_OFF_TRACK` decision caused by a
repeated ambiguous failure is sent to TemporaryGuard. Budgets, empty responses,
finalization violations, and provider errors remain deterministic. Provider
errors, invalid JSON, or invalid actions fall back exactly to the original rule
decision.

### 4. Forward minimal-context processing

Add `aeloon_core/minimal_context.py` with an explicit processor protocol and a
default implementation that:

- retains the leading runtime system prefix and latest compaction checkpoint;
- retains the most recent configured number of complete user turns;
- keeps assistant tool calls paired with their tool results;
- replaces oversized tool results with digest-addressed lazy placeholders while
  the full value remains available through state lazy references;
- filters tool definitions according to `active_tools`;
- returns a fresh call view without mutating canonical state messages.

Backward context compaction continues to run first as a safety net and may
replace canonical messages. Forward processing runs second on the compacted
history and only supplies the current Worker/Guard call.

### 5. Runtime switches and compatibility

Add `agents.defaults.uasm` configuration and CLI setters for:

- `enabled`
- `rule_engine_enabled`
- `temporary_guard_enabled`
- `minimal_context_enabled`
- `transition_trace_enabled`
- guard decision mode and minimal-context bounds

Keep UASM disabled by default so existing deployments remain the unchanged A1
baseline. The experiment presets are:

| Group | UASM | Rule engine | TemporaryGuard | Minimal context |
| --- | --- | --- | --- | --- |
| A0 | on | off | off | off |
| A1 | off (legacy baseline) | existing | off | off |
| A2 | on | on | on | off |
| A3 | on | on | on | on |

The orchestrator selects the legacy kernel or the new state-machine runner and
persists the same `TurnResult` fields, plus non-breaking trace/usage fields with
defaults.

### 6. Fault-injection microbenchmark

Add a deterministic scripted fault-injection module and an offline benchmark
entry point covering:

- fail N times then succeed;
- timeout N times then succeed;
- duplicate-loop and malformed-call scenarios;
- mixed successful and failed tool batches.

Run A0-A3 on identical scripts and report success, recovery after first tool
failure, iterations, unproductive rounds, domain/harness/context token totals,
and transition counts. Use fixed scripts/seeds and no external model calls.

## Implementation sequence

1. Add state, guard-state ownership, transition/usage primitives, and unit tests.
2. Implement Master/Worker/Tool state-machine runner while preserving legacy
   kernel results and hook ordering.
3. Add trace persistence and compaction/domain usage attribution.
4. Add TemporaryGuard escalation and fallback behavior.
5. Add forward MinimalContextProcessor and lazy result references.
6. Wire configuration, CLI, orchestrator, session persistence, and README.
7. Add fault-injection fixtures/benchmark and A0-A3 tests.

## Verification

- Existing full suite remains green.
- Golden compatibility tests compare legacy and UASM A1 final content, tools
  used, canonical message order, budgets, finalization, and error recovery.
- Transition tests verify deterministic sequence, digests, node kinds, schema,
  status, and exactly one visible final hook.
- Guard tests verify no call on first/recoverable deterministic failure, call at
  the ambiguity threshold, continue/terminate behavior, and exact fallback on
  invalid/error responses.
- Context tests verify no canonical-history mutation, no orphan tool messages,
  active-tool filtering, large-result lazy references, and before/after token
  estimates.
- Session tests verify traces are separate and do not affect session turn counts
  or titles.
- Run `uv run pytest -q`, `uv run ruff check .`, and `uv build`.
- Browser verification is only applicable if the change introduces or alters a
  browser-facing surface; this repository currently exposes terminal interfaces.

## Risks to watch

- Accidentally persisting forward-minimized history instead of canonical history.
- Hiding mutable guard counters outside `LightweightState`.
- Persisting temporary finalization prompts into the transcript.
- Double-emitting `on_final` or changing legacy terminal messages.
- Treating pure context estimates as billed provider token usage.
- Allowing a guard response to inject arbitrary prompts or final content.
